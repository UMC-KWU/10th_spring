- ## 세션과 토큰의 차이는?
    
    ### 1. 세션(Session) 인증 방식
    
    > **"사용자의 로그인 상태를 서버가 기억하고 책임진다."**
    > 
    1. **인증 흐름**
        - 유저가 로그인에 성공하면, 서버는 메모리(또는 DB/Redis)에 세션 객체를 생성하고 고유한 **세션 ID(Session ID)**를 발급합니다.
        - 서버는 이 세션 ID를 클라이언트에게 보냅니다. 브라우저는 이를 **쿠키(Cookie)**에 저장합니다.
        - 이후 클라이언트는 매 요청마다 쿠키에 세션 ID를 담아 서버에 보냅니다.
        - 서버는 요청에 담긴 세션 ID가 자신의 세션 스토어에 있는지 확인하여 유저를 식별합니다.
    - **장점**
        - **높은 보안성**: 실제 중요한 유저 정보는 서버에만 있고, 클라이언트는 무작위 문자열인 세션 ID만 가지므로 가로채여도 비교적 안전합니다.
        - **통제 용이성**: 특정 유저의 세션을 서버에서 강제로 만료(로그아웃)시키거나 차단하기 매우 쉽습니다.
    - **단점**
        - **서버 확장성 문제(Scalability)**: 유저가 많아질수록 서버 메모리 부담이 커집니다. 특히 서버를 여러 대 두는 분산 환경(Scale-out)에서 세션 상태를 동기화(Session Clustering)하는 작업이 매우 까다롭습니다.
        - **CORS 문제**: 쿠키는 멀티 도메인(웹과 앱 동시 서비스 등) 환경에서 공유하기 까다롭습니다.
    
    ---
    
    ### 2. 토큰(Token) 인증 방식 (JWT)
    
    > **"서버는 기억하지 않는다. 클라이언트가 제출한 영수증만 검증한다."**
    > 
    1. **인증 흐름**
        - 유저가 로그인에 성공하면, 서버는 유저의 정보와 권한을 담아 암호화된 문자열인 **토큰(주로 JWT - JSON Web Token)**을 발행합니다.
        - 서버는 이 토큰을 따로 저장하지 않고(Stateful -> Stateless), 클라이언트에게 그대로 던져줍니다.
        - 클라이언트는 이 토큰을 로컬 스토리지나 쿠키에 저장합니다.
        - 이후 매 요청마다 HTTP 헤더(`Authorization: Bearer <Token>`)에 토큰을 담아 보냅니다.
        - 서버는 토큰이 자신이 발급한 비밀키(Secret Key)로 서명된 것이 맞는지 **수학적으로 검증만** 하여 유저를 식별합니다.
    - **장점**
        - **무상태성(Stateless)과 확장성**: 서버가 유저의 상태를 기억할 필요가 없으므로 서버 메모리를 아낄 수 있고, 서버가 100대로 늘어나도 비밀키만 공유하면 되므로 분산 환경에 최적화되어 있습니다.
        - **플랫폼 독립성**: 쿠키 제약이 없기 때문에 웹 브라우저뿐만 아니라 안드로이드/iOS 앱, 외부 서버 간 통신(API)에서도 매끄럽게 작동합니다.
    - **단점**
        - **통제 불가 (강제 로그아웃의 어려움)**: 토큰이 한 번 발급되면 만료될 때까지 서버가 이를 강제로 무효화하기 어렵습니다. (이를 보완하기 위해 만료 기간이 짧은 Access Token과 긴 Refresh Token을 조합하여 사용합니다.)
        - **네트워크 트래픽**: 토큰 내부에 유저 정보가 담기기 때문에 세션 ID에 비해 문자열이 길어, 매 요청마다 데이터 전송량이 약간 증가합니다.
    
    ---
    
    | 비교 항목 | 세션 (Session) 기반 인증 | 토큰 (Token / JWT) 기반 인증 |
    | --- | --- | --- |
    | **인증 정보 저장소** | **서버** (메모리, DB, Redis 등) | **클라이언트** (로컬 스토리지, 쿠키 등) |
    | **서버의 상태 유지** | **Stateful** (상태를 계속 기억함) | **Stateless** (요청만 받고 잊어버림) |
    | **서버 확장성** | 낮음 (서버 다중화 시 세션 공유 설정 필요) | **높음** (어떤 서버로 요청이 가도 검증 가능) |
    | **특정 유저 제어** | **가능** (서버에서 세션 삭제 시 즉시 차단) | **어려움** (만료 전까지 토큰 자체는 유효함) |
    | **주요 사용처** | 단일 웹 애플리케이션, 전통적인 MVC 패턴 | **REST API, MSA(마이크로서비스), 모바일 앱 연동** |

    
- ## 엑세스 토큰과 리프레시 토큰이란?
    
    # Access Token vs Refresh Token이란?
    
    토큰 기반 인증(JWT) 방식에서 **보안성**과 **사용자 편의성**을 동시에 챙기기 위해 이중으로 운영하는 두 가지 종류의 토큰입니다.
    
    ---
    
    ### 1. 한 줄 요약
    
    - **Access Token**: API 요청 시 유저의 인증 권한을 확인하는 **'실제 출입증'** (수명이 매우 짧음)
    - **Refresh Token**: Access Token이 만료되었을 때 새 Access Token을 발급받기 위한 **'출입증 발급증명서'** (수명이 매우 길며, 서버에도 저장됨)
    
    ---
    
    ### 2. 왜 토큰을 두 개나 나누어 쓸까요? (도입 배경)
    
    만약 **Access Token 하나만 사용한다면** 두 가지 딜레마에 빠지게 됩니다.
    
    1. **토큰의 유효기간을 길게 잡을 경우 (예: 30일)**
        - **보안 취약**: 만약 해커에게 토큰을 탈취당하면, 해커는 30일 동안 아무런 제약 없이 유저의 계정으로 서버에 마음대로 접근할 수 있습니다. 앞서 배웠듯 stateless 특성상 서버가 이미 발급된 토큰을 강제로 만료시키기도 어렵습니다.
    2. **토큰의 유효기간을 짧게 잡을 경우 (예: 30분)**
        - **UX(사용자 경험) 저하**: 유저는 보안상 안전할지 몰라도, 30분마다 토큰이 만료되어 **30분마다 자꾸 로그아웃이 되고 다시 로그인을 해야 하는** 최악의 경험을 하게 됩니다.
    
    > **해결책**: 평소에 쓰는 출입증(**Access Token**)은 수명을 30분~1시간으로 극단적으로 짧게 잡고, 이게 만료되면 유저 몰래 뒷단에서 긴 수명(1~2주)을 가진 **Refresh Token**을 통해 출입증을 새로 갱신(Refresh)해 주는 방식을 채택한 것입니다.
    > 
    
    ---
    
    ### 3. 두 토큰의 특징 비교
    
    ### 1) Access Token (액세스 토큰)
    
    - **역할**: 클라이언트가 서버의 보호된 자원(API)에 접근할 때 HTTP 헤더에 담아 보내는 실제 인증 토큰입니다.
    - **유효 기간**: 보통 **30분 ~ 2시간** 내외로 매우 짧습니다.
    - **저장 위치**: 클라이언트(메모리 변수, LocalStorage 등)에 저장됩니다. 서버는 이를 따로 저장하지 않고 수학적 검증만 수행합니다.
    
    ### 2) Refresh Token (리프레시 토큰)
    
    - **역할**: Access Token이 만료되었을 때, 클라이언트가 로그인 창을 다시 띄우지 않고 새로운 Access Token을 재발급받기 위해 사용됩니다.
    - **유효 기간**: 보통 **1주 ~ 2주** 정도로 매우 깁니다.
    - **저장 위치**: 클라이언트뿐만 아니라, 서버(일반적으로 Redis 같은 인메모리 DB)에도 복사본을 저장해 둡니다. (만약 탈취당한 것이 확인되면 서버 측 저장소에서 해당 Refresh Token을 삭제하여 강제 로그아웃을 시킬 수 있는 최소한의 통제 수단이 됩니다.)
    
    ---
    
    ### 4. 전체 인증 및 갱신 흐름
    
    1. **최초 로그인**: 유저가 ID/PW로 로그인을 시도하여 성공하면, 서버는 수명이 짧은 `Access Token`과 수명이 긴 `Refresh Token`을 둘 다 발급합니다.
    2. **서비스 이용**: 클라이언트는 `Access Token`을 헤더에 실어 서버에 API 요청을 보냅니다.
    3. **토큰 만료**: 시간이 흘러 `Access Token`이 만료되면, 서버는 클라이언트에게 **"401 Unauthorized (토큰 만료)"** 에러를 응답합니다.
    4. **자동 재발급 요청**: 클라이언트(프론트엔드)는 유저에게 로그인 창을 띄우는 대신, 보관하고 있던 `Refresh Token`을 담아 서버의 토큰 재발급 엔드포인트(ex: `/api/v1/auth/refresh`)로 요청을 보냅니다.
    5. **검증 및 발급**: 서버는 넘어온 `Refresh Token`이 유효하고 DB에 저장된 것과 일치하는지 확인한 후, **새로운 `Access Token`을 재발급**하여 돌려줍니다.
    6. **요청 재시도**: 클라이언트는 새로 받은 `Access Token`으로 유저가 원래 하려던 API 요청을 다시 수행합니다. (유저는 로그아웃 없이 서비스를 계속 이용하게 됩니다.)
    
    ---
    
    ### 5.  차이점 요약
    
    | 구분 | Access Token | Refresh Token |
    | --- | --- | --- |
    | **목적** | API 요청을 통한 리소스 접근 권한 인증 | 만료된 Access Token 재발급 |
    | **유효 기간** | **짧음** (30분 ~ 2시간) | **길음** (1주 ~ 2주) |
    | **전송 빈도** | **매 HTTP 요청마다** 헤더에 실려 전송됨 | Access Token이 만료되었을 때 **어쩌다 한 번** 전송됨 |
    | **탈취 위험성** | 자주 네트워크를 오가므로 탈취 위험 높음 | 전송 빈도가 낮아 탈취 위험이 상대적으로 낮음 |
    | **서버 저장 여부** | 저장 안 함 (Stateless) | **저장함** (Redis 등을 통해 보안 제어용으로 활용) |
    
- ## OAuth 1.0과 OAuth 2.0의 차이는?
    
    # OAuth 1.0 vs OAuth 2.0의 차이는?
    
    - OAuth(Open Authorization)는 애플리케이션(Client)이 사용자의 비밀번호를 직접 받지 않고, 구글·카카오·네이버 같은 인증 서버(Provider)를 통해 안전하게 권한을 부여받기 위한 **오픈 표준 프로토콜**입니다.
    
    1.0 버전의 한계를 극복하고 현대 웹 아키텍처에 맞게 완전히 새로 설계된 것이 현재 우리가 사용하는 2.0 버전입니다.
    
    ---
    
    ### 1. 한 줄 요약
    
    - **OAuth 1.0**: 웹 브라우저 환경에만 맞춰 설계되어 복잡한 암호화 계산(Signature)을 매 요청마다 수행하는 **비교적 느리고 무거운 방식**
    - **OAuth 2.0**: 모바일 앱, 대형 아키텍처(MSA)를 지원하며, 복잡한 암호화를 빼고 **HTTPS(SSL/TLS)와 Access Token 기반으로 단순화하여 대폭 표준화된 방식**
    
    ---
    
    ### 2. OAuth 1.0의 특징과 한계
    
    > **"모바일이 없던 시절, 오직 웹 브라우저와 복잡한 암호화 서명에 의존하던 방식"**
    > 
    - **웹 기반 설계**: 스마트폰(모바일 앱)이 대중화되기 전에 만들어졌기 때문에, 오직 웹 브라우저 환경만 고려하여 설계되었습니다.
    - **복잡한 서명(Signature) 메커니즘**: HTTPS(암호화 통신)가 대중화되지 않았던 시절이라, 보안을 위해 매번 요청을 보낼 때마다 모든 파라미터를 조합하여 복잡한 암호화 서명(`HMAC-SHA1` 등)을 생성해서 생성된 값을 헤더에 실어 보내야 했습니다.
    - **단일 토큰 운영**: 토큰의 개념이 세분화되어 있지 않아 토큰이 만료되면 유저가 무조건 다시 로그인 과정을 거쳐 권한을 갱신해야 했습니다.
    
    **결과**: 구현하기가 너무 까다롭고 컴퓨터 연산 낭비가 심했으며, 모바일 앱이나 백엔드 서버 간 API 통신에 적용하기가 매우 부적합했습니다.
    
    ---
    
    ### 3. OAuth 2.0의 핵심 개선점 및 특징
    
    > **"현대 웹/앱 생태계의 표준. 단순함, 유연성, 그리고 확장성"**
    > 
    - **HTTPS 기반 보안 통합**: 매 요청마다 서명을 계산하는 대신, 네트워크 통신 자체를 **HTTPS로 강제**함으로써 보안을 하드웨어/프로토콜 계층으로 넘겼습니다. 덕분에 개발자는 복잡한 서명 로직을 짤 필요가 없어졌습니다.
    - **토큰의 역할 세분화**: 앞서 배운 **Access Token**과 **Refresh Token**의 개념이 바로 OAuth 2.0 스펙에서 정식으로 정의되었습니다. 유저의 편의성과 보안성을 모두 잡을 수 있게 되었습니다.
    - **다양한 승인 방식(Grant Types) 지원**: 클라이언트의 환경에 따라 권한을 얻는 방식을 4가지 이상으로 세분화했습니다.
        - *Authorization Code Grant* (가장 중요, SpringBoot 백엔드가 있는 웹에 사용)
        - *Implicit Grant* (자바스크립트 기반 단일 페이지 앱(SPA)용)
        - *Resource Owner Password Credentials Grant* (서버와 앱이 완전히 같은 회사일 때 로그인)
        - *Client Credentials Grant* (사용자 없이 서버와 서버 간 통신할 때)
    
    ---
    
    ### 4. 차이점 비교
    
    | 비교 항목 | OAuth 1.0 | OAuth 2.0 |
    | --- | --- | --- |
    | **보안 메커니즘** | 매 API 요청마다 **복잡한 서명(Signature) 생성** 필요 | **HTTPS** 프로토콜에 암호화를 위임하여 단순화 |
    | **토큰 형태** | 서명 기반의 특수 토큰 체계 | 암호화된 일반 문자열 토큰 (**주로 JWT 사용**) |
    | **토큰 만료 분리** | 토큰 만료 시 재로그인 필요 (구조 복잡) | **Access / Refresh Token** 구조로 무중단 자동 갱신 가능 |
    | **지원 플랫폼** | 오직 웹 브라우저(Web) 중심 | **모바일 앱(App), 웹, MSA, 스마트TV 등** 다양한 플랫폼 |
    | **서버 역할 분리** | 인증 서버와 API 서버가 한 덩어리로 붙어있어야 함 | 인증 서버(Authorization Server)와 자원 서버(Resource Server)의 분리 가능 |
    | **구현 난이도** | 매우 복잡하고 정교한 암호화 지식 필요 | 비교적 가볍고 직관적이어서 **구현이 매우 쉬움** |
    
    ---
    
    ### 5. OAuth 2.0 대표 흐름 (Authorization Code 트랙)
    
    SpringBoot 프로젝트에서 구글/카카오 소셜 로그인을 붙일 때 사용하는 표준 흐름입니다.
    
    1. **로그인 요청**: 유저가 우리 서비스(Client)에서 '카카오 로그인' 버튼을 누릅니다.
    2. **인증 및 동의**: 카카오 로그인 창이 뜨고, 유저가 아이디/비밀번호를 치고 '권한 동의'를 누릅니다.
    3. **인가 코드 발급**: 카카오 서버가 우리 SpringBoot 백엔드로 일회용 영수증인 **Authorization Code**를 던져줍니다.
    4. **토큰 교환**: SpringBoot 서버가 백엔드 단에서 방금 받은 인가 코드와 우리의 Secret Key를 카카오 인증 서버로 보내며 "진짜 토큰으로 바꿔주세요"라고 요청합니다.
    5. **Access Token 획득**: 카카오가 검증 후 `Access Token`을 발급해 주면, 우리 백엔드는 이 토큰으로 카카오 API 서버에서 유저의 이메일이나 프로필 사진을 안전하게 긁어와 가입/로그인 처리를 완료합니다.
