- 세션과 토큰의 차이는?


### 세션(Session) vs 토큰(Token)

### 핵심 차이: 상태 저장 위치

**세션 (Session) 방식: "서버가 기억하는 방식"**
**토큰 (Token / 주로 JWT) 방식: "토큰이 기억하는 방식”**

|  | 세션 | 토큰 |
| --- | --- | --- |
| 상태 저장 위치 | **서버** | **클라이언트** |
| 방식 | Stateful | Stateless |
| 대표 예시 | Session ID (쿠키) | JWT (JSON Web Token) |

### 세션 (Session)

1. 사용자가 로그인하면 서버가 세션을 생성하고 **서버 메모리/DB에 저장**
2. 클라이언트는 **세션 ID만** 쿠키로 받음
3. 요청마다 서버가 세션 ID로 저장된 정보를 조회

**장점:** 즉시 무효화 가능, 민감 정보 서버에만 보관

**단점:** 서버 부하, 수평 확장 어려움 (여러 서버 간 세션 공유 필요)

### 토큰 (Token / JWT)

1. 로그인 시 서버가 **사용자 정보를 암호화한 토큰**을 발급
2. 클라이언트가 토큰을 저장 (localStorage, 쿠키 등)
3. 요청마다 토큰을 함께 전송 → 서버는 **서명 검증만** 수행

**장점:** 서버 무상태(stateless), 수평 확장 쉬움, 마이크로서비스에 유리

**단점:** 토큰 탈취 시 만료 전까지 무효화 어려움, 토큰 크기가 큼

- 엑세스 토큰과 리프레시 토큰이란?

  토큰 기반 인증(주로 JWT)을 실제로 구현할 때 보안을 한 단계 더 강화하기 위해 사용하는 조합으로 액세스 토큰과 리프레시 토큰을 같이 이용.

  ### 액세스 토큰 (Access Token)

  **정의**: 보호된 리소스에 접근할 권한을 증명하는 단기 자격증명. API 요청 시 `Authorization: Bearer <token>` 헤더에 담아 전송.

    - 사용자가 로그인되어 있는지 확인하고, API를 요청할 때 실제로 서버에 보여주는 토큰.
    - 클라이언트가 요청을 보낼 때마다 HTTP 헤더에 실림
      ⇒ 탈취당할 위험이 상대적으로 높기 때문에 수명을 짧게 잡음.
    - 만료 전 강제 무효화가 어렵다는 단점.

  ### 리프레시 토큰 (Refresh Token)

  **정의**: 액세스 토큰이 만료됐을 때 재로그인 없이 새 액세스 토큰을 발급받기 위한 장기 자격증명.
  API 호출에는 절대 사용하지 않고, 오직 토큰 재발급 엔드포인트(`/auth/refresh`)에만 사용.

    - 액세스 토큰이 만료되었을 때, 새로운 액세스 토큰을 재발급받기 위한 인증용 토큰.
    - 평소 API요청에 사용되지 않기 때문에 탈취 위험이 낮음

  ## 두 토큰의 작동 흐름 (인증 시나리오)

    1. **로그인 성공:** 사용자가 로그인하면 서버는 **액세스 토큰**과 **리프레시 토큰** 2개를 모두 발급합니다. (리프레시 토큰은 서버 DB에도 저장해 둡니다.)
    2. **일반적인 요청:** 클라이언트는 수명이 짧은 **액세스 토큰**만 사용해서 서버와 통신합니다.
    3. **액세스 토큰 만료:** 1시간이 지나 액세스 토큰이 만료되면, 서버는 `401 Unauthorized`(미인증) 에러를 보냅니다.
    4. **토큰 재발급 요청:** 클라이언트는 에러를 확인하고, 보관해 두었던 **리프레시 토큰**을 서버로 보냅니다.
    5. **검증 및 재발급:** 서버는 DB에 저장된 리프레시 토큰과 일치하는지 확인한 후, 올바르다면 **새로운 액세스 토큰**을 발급해 줍니다.
    6. **활동 재개:** 사용자는 로그아웃되지 않고(사용자는 눈치채지 못함) 새 토큰으로 서비스를 계속 이용합니다.

- OAuth 1.0과 OAuth 2.0의 차이는?

  **OAuth 1.0**과 **OAuth 2.0**은 외부 어플리케이션이 사용자의 비밀번호 없이 권한을 위임받을 수 있도록 하는 인증 표준 프로토콜.

  이름은 비슷하지만, 내부 구조와 철학이 완전히 다름.

  ### **1. 보안을 보장하는 방식(가장 큰 차이)**

  **OAuth 1.0 — 서명(Signature) 방식**

  모든 요청에 `consumer secret`과 `token secret`을 이용해 HMAC-SHA1 서명을 직접 생성. HTTPS 없이도 요청 위변조를 막을 수 있지만, 서명 생성 로직을 클라이언트가 직접 구현해야 해서 복잡. 타임스탬프와 `nonce`(일회성 난수)를 함께 포함해 재전송 공격도 방어.

    ```java
    서명 = HMAC-SHA1(
      HTTP_메서드 + 요청_URL + 파라미터들,
      consumer_secret + "&" + token_secret
    )
    ```

  **OAuth 2.0 — HTTPS 전송 암호화 방식**

  서명 로직을 없애고, 보안을 전적으로 HTTPS(TLS)에 위임. 구현이 단순해진 대신 HTTPS가 필수. Bearer 토큰을 헤더에 담아 전송하는 것만으로 인증이 완료됨.

    ```java
    Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
    ```

  ### **2. 역할의 분리**

    - **OAuth 1.0:** 인증을 처리하는 서버와 데이터를 제공하는 서버가 하나로 묶여 있는 구조.
    - **OAuth 2.0:** 인증 서버(Authorization Server)와 자원 서버(Resource Server)의 역할이 공식적으로 분리됨. 덕분에 대규모 서비스에서는 인증만 전담하는 서버를 따로 두고, 데이터 서버를 여러 대 확장하기가 훨씬 유리해졌음.

  ### 3. 토큰의 수명

  **OAuth 1.0**에서는 한 번 발급받은 토큰의 수명이 매우 길거나 만료되지 않는 경우가 많아, 토큰이 노출되면 보안에 취약했음.

  **OAuth 2.0**은 액세스 토큰과 리프레시 토큰을 이용해 보안성을 강화.

  | **구분** | **OAuth 1.0** | **OAuth 2.0** |
      | --- | --- | --- |
  | **보안 메커니즘** | 암호화 서명(Signature) 필수 생성 | **HTTPS(SSL/TLS)** 암호화에 의존, 서명 없음 |
  | **개발 편의성** | 복잡함 (서명 생성 로직 구현이 까다로움) | **단순함** (헤더에 토큰만 넣어 전송) |
  | **지원 환경** | 웹 브라우저 중심 | 웹, 모바일 앱, 데스크톱, IoT 등 **다양한 환경** |
  | **서버 구조** | 인증 서버와 자원 서버가 일체형 | **인증 서버와 자원 서버의 분리** |
  | **토큰 만료** | 토큰이 수개월~평생 지속되는 경우 많음 | **Access / Refresh Token**으로 수명 분리 관리 |
