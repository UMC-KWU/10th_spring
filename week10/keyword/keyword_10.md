- 클라우드 컴퓨팅이란?

  ## **클라우드 컴퓨팅이란?**

  클라우드 컴퓨팅은 **인터넷을 통해 서버, 저장공간, 데이터베이스, 네트워크, 소프트웨어 같은 IT 자원을 빌려 쓰는 방식**이다.

  즉, 내 컴퓨터나 회사 내부 서버에 직접 설치하지 않아도, 필요한 만큼 클라우드 사업자의 자원을 사용하고 비용을 지불하는 구조다.

  예를 들면 AWS, Microsoft Azure, Google Cloud 같은 서비스가 대표적이다.

  ## 클라우드 컴퓨팅의 핵심 특징

  ### 1. 주문형 셀프 서비스

  사용자가 필요할 때 직접 서버, 저장공간 등을 생성하고 사용할 수 있다.

  예를 들어 웹사이트 운영을 위해 서버가 필요하면 콘솔에서 몇 번 클릭하거나 명령어로 서버를 만들 수 있다.

  ### 2. 광범위한 네트워크 접근

  인터넷만 연결되어 있으면 어디서든 클라우드 자원에 접근할 수 있다.

  ### 3. 자원 공유

  클라우드 사업자의 대규모 서버 자원을 여러 사용자가 나눠 쓴다.

  단, 사용자별 데이터와 환경은 논리적으로 분리된다.

  ### 4. 빠른 확장성

  사용량이 늘어나면 서버, 저장공간, 처리 능력을 빠르게 늘릴 수 있다.

  반대로 사용량이 줄면 자원을 줄여 비용을 아낄 수 있다.

  ### 5. 사용량 기반 과금

  사용한 만큼 비용을 지불한다.

  서버를 1시간만 사용하면 1시간 비용만 내는 식이다.
    
  ---

  ## 클라우드 서비스 모델

  ### 1. IaaS

  Infrastructure as a Service.

  서버, 저장공간, 네트워크 같은 **인프라**를 빌려 쓰는 방식이다.

  사용자는 운영체제, 런타임, 애플리케이션을 직접 관리한다.

  예시: AWS EC2, Azure Virtual Machines, Google Compute Engine
    
  ---

  ### 2. PaaS

  Platform as a Service.

  개발자가 애플리케이션을 배포할 수 있는 **플랫폼 환경**을 제공하는 방식이다.

  서버나 운영체제 관리는 클라우드 사업자가 맡고, 사용자는 코드와 애플리케이션에 집중한다.

  예시: Heroku, Google App Engine, AWS Elastic Beanstalk
    
  ---

  ### 3. SaaS

  Software as a Service.

  완성된 **소프트웨어**를 인터넷으로 사용하는 방식이다.

  사용자는 설치나 서버 관리 없이 로그인해서 서비스를 사용한다.

  예시: Gmail, Google Drive, Notion, Slack
    
  ---

  ## 배포 모델

  ### 1. 퍼블릭 클라우드

  AWS, Azure, Google Cloud처럼 외부 클라우드 사업자의 자원을 여러 사용자가 함께 사용하는 방식이다.

  비용이 비교적 저렴하고 확장성이 좋다.

  ### 2. 프라이빗 클라우드

  특정 조직만 사용하는 클라우드 환경이다.

  보안과 통제력이 높지만 구축 비용이 크다.

  ### 3. 하이브리드 클라우드

  퍼블릭 클라우드와 프라이빗 클라우드를 함께 사용하는 방식이다.

  중요한 데이터는 내부에 두고, 외부 서비스는 퍼블릭 클라우드를 쓰는 식이다.

  ### 4. 멀티 클라우드

  두 개 이상의 클라우드 사업자를 함께 사용하는 방식이다.

  예를 들어 AWS와 Azure를 동시에 사용하는 구조다.
    
  ---

  ## 클라우드 컴퓨팅의 장점

  ### 1. 초기 비용 절감

  서버를 직접 구매하지 않아도 되므로 초기 투자 비용이 줄어든다.

  ### 2. 확장성

  사용자가 많아지면 서버를 늘리고, 적어지면 줄일 수 있다.

  ### 3. 빠른 구축

  서버나 DB를 몇 분 안에 생성할 수 있다.

  ### 4. 유지보수 부담 감소

  물리적 서버 관리, 하드웨어 교체, 일부 보안 업데이트 등을 클라우드 사업자가 담당한다.

  ### 5. 접근성

  인터넷만 있으면 어디서든 서비스에 접근할 수 있다.
    
  ---

  ## 클라우드 컴퓨팅의 단점

  ### 1. 인터넷 의존성

  네트워크가 불안정하면 서비스 이용에 문제가 생길 수 있다.

  ### 2. 비용 관리 어려움

  사용량이 많아지면 예상보다 비용이 크게 나올 수 있다.

  ### 3. 보안 문제

  데이터를 외부 클라우드에 저장하므로 접근 권한, 암호화, 인증 관리가 중요하다.

  ### 4. 벤더 종속성

  특정 클라우드 사업자의 기술에 의존하면 다른 클라우드로 이전하기 어려울 수 있다.

- AWS? GCP?

  AWS와 GCP는 대표적인 **클라우드 컴퓨팅 플랫폼**이다.

  기업이나 개발자는 서버, 데이터베이스, 스토리지, AI 서비스 등을 직접 구축하지 않고 AWS나 GCP의 자원을 빌려 사용할 수 있다.
    
  ---

  # AWS (Amazon Web Services)

  AWS는 아마존이 제공하는 클라우드 플랫폼이다.

  2006년에 출시되었으며 현재 전 세계에서 가장 높은 시장 점유율을 가지고 있다.
    
  ---

  ## AWS 주요 서비스

  ### EC2 (Elastic Compute Cloud)

  가상 서버 서비스

  쉽게 말해 인터넷으로 빌려 쓰는 컴퓨터이다.

  예시

    - Spring Boot 서버 배포
    - Node.js 서버 배포
    - Python 서버 배포

    ---

  ### S3 (Simple Storage Service)

  객체 스토리지 서비스

  이미지, 동영상, 문서 등을 저장한다.

  예시

    - 프로필 이미지 저장
    - CCTV 영상 저장
    - 백업 파일 저장

    ---

  ### RDS (Relational Database Service)

  관리형 데이터베이스 서비스

  지원 DB

    - MySQL
    - PostgreSQL
    - MariaDB
    - Oracle
    - SQL Server

  예시

    - 여행 앱 DB
    - 쇼핑몰 DB

    ---

  ### Lambda

  서버리스(Serverless) 서비스

  서버를 직접 만들지 않고 코드를 실행할 수 있다.

  예시

    - 이미지 업로드 시 자동 처리
    - 이벤트 발생 시 자동 실행

    ---

  ### CloudFront

  CDN 서비스

  전 세계 사용자에게 콘텐츠를 빠르게 전달한다.
    
  ---

  ## AWS 장점

  ### 서비스 종류가 매우 많음

  200개 이상의 서비스를 제공한다.

  ### 시장 점유율 1위

  사용 사례와 문서가 매우 많다.

  ### 국내 취업 시장에서 많이 사용

  Spring Boot 백엔드 채용 공고에서 AWS 경험을 요구하는 경우가 많다.
    
  ---

  ## AWS 단점

  ### 서비스가 너무 많음

  처음 배우기 어렵다.

  ### 비용 구조가 복잡함

  실수로 비용 폭탄이 나올 수 있다.
    
  ---

  # GCP (Google Cloud Platform)

  GCP는 구글이 제공하는 클라우드 플랫폼이다.
    
  ---

  ## GCP 주요 서비스

  AWS의 EC2와 비슷한 가상 서버 서비스
    
  ---

  ### Cloud Storage

  AWS S3와 비슷한 스토리지 서비스
    
  ---

  ### Cloud SQL

  AWS RDS와 비슷한 관리형 데이터베이스 서비스

  지원 DB

    - MySQL
    - PostgreSQL
    - SQL Server

    ---

  ### Cloud Functions

  AWS Lambda와 비슷한 서버리스 서비스
    
  ---

  ### BigQuery

  GCP의 대표 서비스

  대용량 데이터 분석 플랫폼

  예시

    - AI 데이터 분석
    - 통계 처리

    ---

  ## GCP 장점

  ### 데이터 분석과 AI에 강함

  구글의 AI 기술을 쉽게 활용할 수 있다.

  대표 서비스

    - Gemini
    - Vertex AI
    - BigQuery

    ---

  ### 사용이 비교적 단순함

  AWS보다 UI와 구조가 직관적이라는 평가가 많다.
    
  ---

  ### 네트워크 성능 우수

  ## GCP 단점

  AWS보다 서비스 수가 적음

  국내 레퍼런스가 상대적으로 적음

  취업 시장에서는 AWS가 더 많이 보인다.

- 환경변수 처리 방법과 왜 환경변수로 민감 정보를 가려야 하는가?

  # 환경변수(Environment Variable)란?

  환경변수는 **프로그램 실행 시 필요한 설정값을 코드 밖에서 관리하는 방법**이다.

  예를 들어 다음과 같은 정보들을 환경변수로 관리한다.

    - DB 주소
    - DB 계정
    - DB 비밀번호
    - JWT Secret Key
    - AWS Access Key
    - AWS Secret Key
    - API Key
    - 서버 포트 번호

    ---

  # 왜 환경변수로 민감 정보를 숨기는가?

  ## 1. 보안

  가장 큰 이유이다.

  만약 GitHub에 다음 코드가 올라가면

    ```java
    private static final String DB_PASSWORD = "1234";
    ```

  누구나 DB에 접속할 수 있다.

  특히

    - AWS Access Key
    - Secret Key
    - JWT Secret
    - API Key

  같은 정보가 유출되면 큰 피해가 발생한다.
    
  ---

  ## 2. 운영 환경과 개발 환경 분리

  개발 서버

    ```
    DB_HOST=localhost
    ```

  운영 서버

    ```
    DB_HOST=prod-db.company.com
    ```

  코드는 동일하고 환경변수만 바꾸면 된다.
    
  ---

  ## 3. 유지보수 편의성

  DB 비밀번호가 변경되더라도

    ```
    DB_PASSWORD=new_password
    ```

  만 수정하면 된다.

  소스코드를 수정하거나 재배포할 필요가 줄어든다.
    
  ---

  # AWS와 환경변수

  AWS에서는 환경변수가 더욱 중요하다.

  ## 사례 1 : EC2

  Spring Boot 서버를 EC2에 배포했다고 가정

  ### 잘못된 방식

    ```java
    private static final String AWS_SECRET_KEY = "xxxxxxxx";
    ```

  만약 서버 코드가 유출되면

  AWS 계정까지 위험해진다.
    
  ---

  ### 올바른 방식

  EC2 환경변수 등록

    ```
    export DB_URL=...
    export JWT_SECRET=...
    ```

  Spring

    ```
    jwt.secret=${JWT_SECRET}
    ```
    
  ---

  ## 사례 2 : Docker + EC2

  ### .env

    ```
    DB_URL=...
    DB_USER=...
    DB_PASSWORD=...
    ```

  ### docker-compose

    ```
    services:
      app:
        env_file:
          - .env
    ```

  컨테이너가 환경변수를 읽어서 실행한다.
    
  ---

  ## 사례 3 : AWS Lambda

  Lambda에서는 콘솔에서 환경변수를 설정할 수 있다.

  예시

    ```
    JWT_SECRET
    DB_HOST
    API_KEY
    ```

  코드에서는

    ```
    process.env.JWT_SECRET
    ```

  으로 읽는다.
    
  ---

  ## 사례 4 : GitHub Actions

  배포 자동화 시

  ### 위험

    ```
    AWS_SECRET_ACCESS_KEY: abcdefg
    ```

  직접 적으면 노출될 수 있다.
    
  ---

  ### 안전

  GitHub Secrets 사용

    ```
    ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    ```

  GitHub이 암호화해서 관리한다.
    
  ---

  # AWS에서 더 좋은 방법 : IAM Role

  실무에서는

    ```
    AWS_ACCESS_KEY_ID
    AWS_SECRET_ACCESS_KEY
    ```

  를 직접 저장하지 않는 경우가 많다.
    
  ---

  ## Access Key 사용

    ```
    AWS_ACCESS_KEY_ID=...
    AWS_SECRET_ACCESS_KEY=...
    ```

  문제점

    - 키 유출 위험
    - 주기적 교체 필요

    ---

  ## IAM Role 사용

  EC2에 IAM Role 부여

    ```
    EC2
     └ IAM Role
          └ S3 접근 권한
    ```

  Spring 코드

    ```
    AmazonS3ClientBuilder.defaultClient();
    ```

  AWS가 자동으로 인증 정보를 제공한다.

  개발자는 Access Key를 저장하지 않는다.
    
  ---

  ## 실무에서 권장

  ### 나쁜 방법

    ```
    AWS_ACCESS_KEY_ID
    AWS_SECRET_ACCESS_KEY
    ```

  ### 좋은 방법

    ```
    EC2
      ↓
    IAM Role
      ↓
    S3 접근
    ```

  AWS 공식 권장 방식이다.

- yml 환경 분리 방법

  # yml 환경 분리란?

  `application.yml`을 **개발 환경, 운영 환경, 테스트 환경별로 나누는 방식**이다.

  예를 들어 DB 주소가 환경마다 다를 수 있다.

    ```yaml
    # 개발 환경
    DB_HOST=localhost
    
    # 운영 환경
    DB_HOST=prod-db.amazonaws.com
    ```

  이걸 코드에서 직접 바꾸지 않고, 실행 환경에 따라 다른 설정 파일을 읽게 하는 것이다.
    
  ---

  # Spring Boot yml 환경 분리 방식

  ## 1. 기본 설정 파일

    ```yaml
    # application.yml
    
    spring:
      profiles:
        active: local
    ```

  또는 공통 설정만 둔다.

    ```yaml
    # application.yml
    
    spring:
      application:
        name: my-app
    
    server:
      port: 8080
    ```
    
  ---

  ## 2. 환경별 yml 파일 생성

    ```
    src/main/resources
     ├ application.yml
     ├ application-local.yml
     ├ application-dev.yml
     └ application-prod.yml
    ```
    
  ---

  ## 3. local 환경 설정

    ```yaml
    # application-local.yml
    
    spring:
      datasource:
        url: jdbc:mysql://localhost:3306/mydb
        username: root
        password: 1234
    ```
    
  ---

  ## 4. dev 환경 설정

    ```yaml
    # application-dev.yml
    
    spring:
      datasource:
        url: jdbc:mysql://dev-db.amazonaws.com:3306/mydb
        username: dev_user
        password: ${DB_PASSWORD}
    ```
    
  ---

  ## 5. prod 환경 설정

    ```yaml
    # application-prod.yml
    
    spring:
      datasource:
        url: jdbc:mysql://prod-db.amazonaws.com:3306/mydb
        username: prod_user
        password: ${DB_PASSWORD}
    ```
    
  ---

  # 실행할 때 profile 지정

  ## 로컬 실행

    ```
    java-jar app.jar--spring.profiles.active=local
    ```

  ## 개발 서버 실행

    ```
    java-jar app.jar--spring.profiles.active=dev
    ```

  ## 운영 서버 실행

    ```
    java-jar app.jar--spring.profiles.active=prod
    ```
    
  ---

  # IntelliJ에서 설정

  Run Configuration에서 VM options 또는 Program arguments에 추가한다.

    ```
    --spring.profiles.active=local
    ```
    
  ---

  # yml에서 환경변수 사용

  민감 정보는 yml에 직접 쓰지 않는다.

  ## 나쁜 예

    ```
    spring:
      datasource:
        password: mypassword123
    ```

  ## 좋은 예

    ```
    spring:
      datasource:
        password: ${DB_PASSWORD}
    ```

  실제 값은 서버 환경변수나 `.env`, AWS Secrets Manager에서 관리한다.

  # AWS와 연결해서 보면

  ## EC2 배포 시

  운영 서버에서는 다음처럼 실행한다.

    ```bash
    export DB_PASSWORD=운영DB비밀번호
    
    java -jar app.jar --spring.profiles.active=prod
    ```

  그러면 Spring Boot는

    ```yaml
    # application-prod.yml
    spring:
      datasource:
        password: ${DB_PASSWORD}
    ```

  여기서 `DB_PASSWORD` 값을 읽는다.

  # 주의할 점

  ## 1. application-prod.yml에 비밀번호 직접 쓰지 않기

  운영 DB 비밀번호, JWT Secret, AWS Key는 절대 직접 작성하지 않는다.
    
  ---

  ## 2. application.yml에 active profile 고정하지 않기

    ```
    spring:
      profiles:
        active: prod
    ```

  이렇게 고정하면 실수로 로컬에서 운영 DB에 붙을 수 있다.

  보통 실행 시점에 지정하는 게 안전하다.
    
  ---

  ## 3. 환경별 파일 이름 규칙 지키기

  Spring Boot는 다음 규칙을 사용한다.

    ```
    application-{profile}.yml
    ```

  예시:

    ```
    application-local.yml
    application-dev.yml
    application-prod.yml
    ```
    
  ---

  # 정리

  yml 환경 분리는 **환경별 설정 파일을 나누고, 실행할 때 profile을 선택해서 필요한 설정만 적용하는 방식**이다.

    ```
    application.yml
    application-local.yml
    application-dev.yml
    application-prod.yml
    ```

  민감 정보는 yml에 직접 쓰지 않고,

    ```
    password: ${DB_PASSWORD}
    ```

  처럼 환경변수로 주입한다.

  ## 한 줄 정리

  Spring Boot에서 yml 환경 분리는 `application-{profile}.yml` 파일을 만들고 `spring.profiles.active`로 실행 환경을 선택하여 개발, 테스트, 운영 설정을 분리하는 방법이다.

- Docker와 .jar vs Docker 이미지

  # Docker란?

  Docker는 애플리케이션을 **실행에 필요한 환경까지 함께 묶어서 실행**할 수 있게 해주는 도구다.

  즉, 코드만 옮기는 게 아니라

    ```
    애플리케이션 코드
    + 실행 환경
    + 라이브러리
    + 설정
    ```

  을 하나로 패키징해서 어디서든 비슷하게 실행할 수 있게 한다.
    
  ---

  # .jar란?

  `.jar`는 Java 애플리케이션을 실행할 수 있게 묶은 파일이다.

  Spring Boot 프로젝트를 빌드하면 보통 다음과 같은 파일이 나온다.

    ```
    app.jar
    ```

  실행은 이렇게 한다.

    ```bash
    java -jar app.jar
    ```

  즉, `.jar`는 **Java 애플리케이션 결과물**이다.
    
  ---

  # Docker 이미지란?

  Docker 이미지는 애플리케이션과 실행 환경을 함께 묶은 실행 패키지다.

  Spring Boot 기준으로 보면 Docker 이미지 안에는 보통 이런 것들이 들어간다.

    ```
    Linux 환경
    JDK 또는 JRE
    app.jar
    실행 명령어
    ```

  즉, Docker 이미지는 단순히 `.jar`만 있는 게 아니라, `.jar`를 실행할 환경까지 포함한다.
    
  ---

  # .jar 실행 방식

    ```
    서버
     └ Java 설치 필요
         └ app.jar 실행
    ```

  실행 예시:

    ```
    java -jar app.jar
    ```

  특징:

    - 서버에 Java가 설치되어 있어야 함
    - Java 버전이 맞아야 함
    - 환경 설정을 서버에서 직접 맞춰야 함
    - 배포는 비교적 단순함
    - 서버 환경 차이로 문제가 생길 수 있음

    ---

  # Docker 이미지 실행 방식

    ```
    서버
     └ Docker 설치 필요
         └ Docker 컨테이너 실행
              └ Java 환경 + app.jar 포함
    ```

  실행 예시:

    ```
    docker run -p 8080:8080 my-app
    ```

  특징:

    - 서버에 Java를 직접 설치하지 않아도 됨
    - 이미지 안에 실행 환경이 포함됨
    - 개발/운영 환경 차이를 줄일 수 있음
    - 배포와 확장이 편리함
    - 컨테이너 기반 운영에 적합함

    ---

  # .jar vs Docker 이미지

  | 구분 | .jar | Docker 이미지 |
      | --- | --- | --- |
  | 의미 | Java 실행 파일 | 실행 환경까지 포함한 패키지 |
  | 필요한 것 | 서버에 Java 필요 | 서버에 Docker 필요 |
  | 포함 범위 | 애플리케이션 코드 중심 | OS 환경, Java, 앱, 실행 명령 |
  | 실행 명령 | `java -jar app.jar` | `docker run 이미지명` |
  | 환경 일관성 | 서버 환경에 영향 받음 | 이미지 기준으로 실행되어 일관성 높음 |
  | 배포 난이도 | 간단함 | 처음 설정은 더 필요 |
  | 확장성 | 직접 관리 필요 | 컨테이너 오케스트레이션과 잘 맞음 |
    
  ---

  # AWS와 연결해서 보면

  ## .jar 배포

  EC2 서버에 접속해서 직접 배포한다.

    ```
    EC2
     ├ Java 설치
     ├ app.jar 업로드
     └ java -jar app.jar 실행
    ```

  장점:

    - 구조가 단순함
    - 처음 배우기 쉬움

  단점:

    - Java 버전 관리 필요
    - 서버 설정을 직접 해야 함
    - 여러 서버에 배포할 때 번거로움

    ---

  ## Docker 이미지 배포

  이미지를 빌드해서 Docker Hub, ECR 등에 올린 뒤 EC2에서 실행한다.

    ```
    개발 PC
     └ Docker 이미지 빌드
          ↓
    AWS ECR
          ↓
    EC2에서 pull
          ↓
    docker run
    ```

  장점:

    - EC2에 Java 설치 불필요
    - 실행 환경이 이미지에 고정됨
    - 배포 자동화에 유리함
    - ECS, EKS 같은 AWS 컨테이너 서비스와 연결 가능

  단점:

    - Dockerfile, 이미지 빌드, 레지스트리 개념을 알아야 함
    - 처음에는 .jar 배포보다 복잡하게 느껴질 수 있음

    ---

  # 정리

  ## Docker

  애플리케이션과 실행 환경을 컨테이너로 묶어 어디서든 일관되게 실행하게 해주는 기술이다.

  ## .jar

  Java 애플리케이션을 빌드한 실행 파일이다.

  ## Docker 이미지

  `.jar`와 Java 실행 환경을 포함하여 컨테이너로 실행할 수 있게 만든 패키지다.

  ## 한 줄 정리

  `.jar`는 Java 애플리케이션 결과물이고, Docker 이미지는 그 `.jar`를 실행하는 데 필요한 환경까지 함께 묶은 배포 단위이다.
