## Spring Security (스프링 시큐리티)

### 1. 정의

> **"스프링 기반 애플리케이션의 보안(인증과 인가)을 책임지는 표준 프레임워크"**
> 
- **정의**: Spring Security는 자바 애플리케이션에서 **인증(Authentication)**, **인가(Authorization)** 및 일반적인 **보안 공격(CSRF, 세션 고정 등) 방어** 기능을 제공하는 강력하고 커스터마이징이 용이한 인증 및 액세스 제어 프레임워크입니다.

### 2. 동작 원리: 필터 체인 (Filter Chain)

Spring Security의 핵심은 핵심 로직(디스패처 서블릿)으로 요청이 가기 전, 앞단에서 요청을 가로채는 Filter(필터)들의 집합체입니다.

- **동작 방식**: 사용자의 HTTP 요청이 들어오면, 여러 개의 보안 필터가 꼬리에 꼬리를 물고 체인 형태로 동작하며 인증/인가를 검증합니다.
- **대표적인 필터**:
    - `UsernamePasswordAuthenticationFilter`: 폼 로그인을 처리하는 필터
    - `BearerTokenAuthenticationFilter`: JWT 토큰 인증을 처리할 때 주로 확장하는 필터
    - `ExceptionTranslationFilter`: 인증/인가 예외를 처리하여 로그인 페이지로 리다이렉트하거나 에러 응답을 생성하는 필터

### 3. 주요 기능 및 특징

- **선언적 보안**: 설정 클래스나 어노테이션(`@PreAuthorize`)을 통해 특정 URL이나 메서드 단위로 권한을 손쉽게 제어할 수 있습니다.
- **다양한 인증 방식 지원**: 기본 Form 로그인뿐만 아니라 JWT, OAuth2(구글, 카카오 로그인 등)와의 연동이 매우 매끄럽습니다.
- **기본적인 보안 공격 방어**:
    - **CSRF(사이트 간 요청 위조)** 방어 토큰 자동 발급
    - **Session Fixation(세션 고정 공격)** 방지
    - HTTP 응답 헤더 보호 (X-Frame-Options 등)
 
### 1. 인증 (Authentication)

> **“Identity Verification”**
> 
- **정의**: 시스템에 접근하려는 사용자가 **'신원이 확인된 올바른 사용자'인지를 증명**하는 과정입니다.
- **핵심 목적**: 유저가 주장하는 신원(아이디 등)이 실제 사실과 일치하는지 확인하여 시스템에 입장시킵니다.
- **대표적인 예시**:
    - 아이디와 비밀번호를 입력하여 로그인하는 행위
    - 스마트폰에 지문이나 페이스 ID를 인식시키는 행위
    - 이메일이나 SMS를 통한 2차 인증 번호 입력
    - 서버가 발급한 JWT 토큰을 요청 헤더에 담아 보내는 행위

### 2. 인가 (Authorization)

> **"당신은 이 행동을 할 자격이 있습니까? (Access Control)"**
> 
- **정의**: 인증을 거친 사용자가 **특정 리소스에 접근하거나 특정 기능(권한)을 수행할 수 있는지 허가**하는 과정입니다.
- **핵심 목적**: 시스템 내부의 자원을 보호하기 위해 사용자 유형(Role)이나 권한(Authority)에 따라 행동의 범위를 제한합니다.
- **대표적인 예시**:
    - 일반 회원은 마이페이지를 볼 수 있지만, 관리자 페이지(`/admin`)에는 들어가지 못함
    - 내가 작성한 글은 수정/삭제할 수 있지만, 타인이 작성한 글은 읽기만 가능함
    - 네이버 카페에서 '새싹멤버'는 글쓰기가 불가능하고 '정멤버'부터 글쓰기가 가능한 규칙

| **비교 항목** | **인증 (Authentication)** | **인가 (Authorization)** |
| --- | --- | --- |
| **주요 대상** | 사용자 자체 (신원 확인) | 사용자의 권한 (행위 허가) |
| **선후 관계** | **반드시 먼저 진행됨 (1단계)** | 인증이 완료된 후 진행됨 (2단계) |
| **데이터 예시** | ID/PW, JWT 토큰, OAuth 인증 정보 | `ROLE_USER`, `ROLE_ADMIN` 같은 권한 등급 |
| **실패 시 HTTP 상태 코드** | **401 Unauthorized** | **403 Forbidden** |

 - ### 1. Stateful (상태 유지)
    
    > **"서버가 클라이언트의 이전 상태를 기억하는 방식"**
    > 
    - **정의**: 서버가 클라이언트와의 대화나 요청 정보를 **지속적으로 보존**하며 다음 요청을 처리하는 아키텍처입니다.
    - **동작 원리**: 클라이언트가 한 번 로그인하면, 서버는 메모리나 세션(Session) 저장소에 그 정보를 저장해 둡니다. 이후 클라이언트의 요청은 해당 상태를 기반으로 처리됩니다.
    - **현실 세계 비유**: 단골 가게 점원
        - 손님: "아메리카노 한 잔 주세요." (점원이 얼굴을 기억함)
        - 손님: "한 잔 더 주세요." -> 점원이 알아서 아메리카노를 한 잔 더 줌.
    - **대표적인 기술**: 전통적인 **웹 세션(Session) & 쿠키(Cookie)** 방식.
    - **치명적인 단점**: **서버 확장성이 떨어짐.** 1번 서버에서 로그인한 유저가 트래픽 분산(로드 밸런싱)으로 인해 2번 서버로 요청을 보내면, 2번 서버는 유저의 로그인 상태를 모르기 때문에 다시 로그인해야 하는 문제가 발생합니다.
    
    ### 2. Stateless (무상태)
    
    > **"서버가 클라이언트의 상태를 저장하지 않는 방식"**
    > 
    - **정의**: 서버가 클라이언트의 이전 요청 상태를 전혀 저장하지 않으며, **모든 요청은 독립적으로 처리**되는 아키텍처입니다.
    - **동작 원리**: 클라이언트는 매 요청마다 **자신이 누구인지 증명할 수 있는 모든 정보(인증 토큰 등)를 요청에 꽉 채워서** 보내야 합니다. 서버는 그 요청만 보고 즉시 처리 후 응답합니다.
    - **현실 세계 비유**: 키오스크나 매번 바뀌는 알바생
        - 손님: "아메리카노 한 잔 주세요." -> 결제 및 제공.
        - 손님: "한 잔 더 주세요." -> 알바생: "어떤 음료 말씀이신가요?" (이전 대화를 기억 못 함)
    - **대표적인 기술**: **HTTP 프로토콜**, **JWT (JSON Web Token)**, REST API.
    - **최고의 장점**: **서버 확장성(Scalability) 극대화.** 서버가 유저의 상태를 보관하지 않으므로, 요청이 1번 서버로 가든 100번 서버로 가든 상관없이 동일하게 응답할 수 있습니다. (Scale-out에 매우 유리)
    
    | **비교 항목** | **Stateful (상태 유지)** | **Stateless (무상태)** |
    | --- | --- | --- |
    | **상태 저장 위치** | **서버** (메모리, 세션 스토어 등) | **클라이언트** (토큰, 로컬 스토리지 등) |
    | **요청 메시지 크기** | 상대적으로 작음 (인증 값만 전송) | 상대적으로 큼 (매번 토큰/정보를 포함) |
    | **서버 확장성** | ❌ 낮음 (서버 간 상태 동기화 비용 발생) | ✅ 매우 높음 (Scale-out이 자유로움) |
    | **장애 복구** | 프로세스 다운 시 유저 세션이 끊김 | 서버가 다운되어도 다른 서버가 즉시 대체 가능 |
    | **대표 인증 수단** | 세션 기반 로그인 (Session ID) | 토큰 기반 로그인 (JWT) |
